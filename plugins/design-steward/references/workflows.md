# 調査・判断ワークフロー

必要なモードの節だけを使う。複数モードにまたがる場合も、同じ調査や記録を重複させない。

## 機能単位の横断確認

利用者または外部システムから見える機能ごとに、次の観点が必要かを確認する。

- 認可: 誰が実行・参照できるか。対象データの所有範囲を越えないか。
- 監査: 誰が、いつ、何を行ったかを記録する必要があるか。
- 不正利用・入力: 想定外入力、過剰利用、権限昇格、情報漏えいへの対策が必要か。
- 同時実行・重複実行: 競合、二重送信、再試行によって重複や矛盾が起きないか。
- 業務整合性: 状態遷移、一意性、上限、前提条件、関連データとの整合性を守れるか。
- 失敗時の扱い: 部分成功、ロールバック、再試行、利用者への通知を定義する必要があるか。

すべての観点について詳細設計や対策を必須としない。該当しない場合は設計を増やさず、判断へ影響する観点だけを成果物へ記録する。

ただし、認可、永続データの不整合、金銭・在庫・権利の重複、取り消し困難な外部操作に関わる場合は、暗黙に省略せず判断を明示する。

## 新規設計

1. ユーザーの目的、利用者、成功条件、制約、対象外を抽出する。
2. 要求を、機能要件、品質要件、運用・移行要件、制約へ整理する。
3. 受け入れ可能な振る舞いを具体化し、曖昧語や互いに矛盾する条件を指摘する。
4. 機能ごとに「機能単位の横断確認」を行い、必要な制約と受け入れ条件を抽出する。
5. 次の高コスト判断を優先する。
   - 永続データの所有権、保持、削除、移行
   - 外部公開するAPI・イベント・ファイル形式
   - 認証、認可、秘密情報、信頼境界
   - コンポーネント境界と重要な責務
   - 可用性、性能、整合性、監査、運用負荷のトレードオフ
   - ベンダーやプラットフォームへの不可逆な依存
6. 高コスト判断の合意後に、必要な深さまで基本設計と詳細設計を進める。実装に不要な将来拡張は設計しない。

## 既存分析

調査対象は依頼に関係する範囲へ絞る。利用可能なら、次を相互に照合する。

- 実行経路と主要なエントリポイント
- DBスキーマ、マイグレーション、データ所有者
- 公開API、イベント、ジョブ、外部連携
- 機能ごとの認可、監査、重複実行、状態遷移、業務制約の実装箇所
- テストが示す観測可能な仕様
- 設定、デプロイ、監視、障害時の挙動
- README、設計資料、ADR、Issueや変更履歴

実装は「現在どう動くか」の証拠であり、「本来どうあるべきか」の証明ではない。文書も同様に古い可能性がある。各主張へ具体的な根拠を添え、食い違いは次の形で残す。

| 状態 | 記録内容 |
|---|---|
| 確認済み | 根拠となるファイル、スキーマ、テスト、実行結果と観測内容 |
| 推定 | 推定した意図、その根拠、確信度、反証になり得る情報 |
| 不整合 | 競合する資料・実装、現在の影響、正とする主体 |
| 未決定 | 決定に必要な質問または不足資料 |

改善案は、現状の欠陥修正、意図への復元、新しい方針への変更を区別する。推定した設計思想を使って実装や正式資料を上書きしない。

## 変更評価

変更案ごとに次を確認する。

1. 対応する目的・要件・受け入れ条件は何か。
2. 既存の原則、責務、データ、契約、セキュリティ境界と矛盾しないか。あわせて、対象機能について認可、監査、不正利用、同時実行、重複実行、業務整合性への影響を確認する。
3. 直接影響と二次影響はどこか。移行、互換性、ロールバック、運用に加え、変更対象を参照する要件、機能設計、全体設計、決定記録、テスト、運用資料、`AGENTS.md` への影響も確認する。
4. 既存設計を維持する案、変更する案、段階移行案のどれが合理的か。
5. 変更しない場合と各代替案の費用・リスクは何か。
6. 事前承認が必要か。必要なら承認前は `提案` として記録する。
7. 変更が承認されたら、影響する既存資料と相互参照を特定し、同じ変更単位で更新する資料と、別途対応が必要な資料を分ける。

## 質問の仕方

調査で解決できる質問は先に調べる。ユーザーへは、回答によって設計が実際に分岐する高影響事項から少数ずつ尋ねる。各質問に次を添える。

- なぜ今決める必要があるか
- 選択肢と主なトレードオフ
- 推奨案と、その前提
- 未回答のまま進められる範囲

## 設計レベル

- **要件定義**: 目的、利用者、振る舞い、品質、制約、対象外、受け入れ条件。実装方法を確定しない。
- **基本設計**: システム境界、コンポーネント責務、データ所有、外部契約、主要フロー、横断的方針。
- **詳細設計**: 内部のデータ構造、処理順序、状態遷移、エラー処理、アルゴリズム、実装単位の契約。

依頼と次の実装判断に必要なレベルまで記述する。情報がない箇所を埋めるためだけに詳細化しない。
