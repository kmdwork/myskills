# 成果物の選択と最小テンプレート

既存資料を優先し、同じ役割のファイルがある場合は新しい体系を追加せず更新候補を示す。ファイル名はプロジェクト規約へ合わせる。

## 選択基準

| 成果物 | 作る・更新する条件 |
|---|---|
| `AGENTS.md` | Codexが複数作業で継続して守る必要がある、短い実行規則がある |
| `docs/constitution.md` | プロダクト目的や設計原則が、個別機能を越えて判断を制約する |
| `docs/architecture.md` | システム境界、責務、データ・依存関係の全体像を共有する必要がある |
| `docs/decisions.md` | 複数の重要判断を軽量に記録する。既存ADRがあればそちらを使う |
| `specs/<feature>/spec.md` | 機能の目的、要件、対象外、受け入れ条件を独立して管理する価値がある |
| `specs/<feature>/design.md` | 機能固有の責務、データ、契約、主要フロー、例外を残す必要がある |
| `specs/<feature>/tasks.md` | 合意済み設計を複数の検証可能な実装単位へ分解する必要がある |

小規模な変更なら、既存Issueや単一の仕様書の節だけで十分なことがある。空のファイルや将来用の雛形は作らない。

## 共通の状態表現

主張や判断に必要な場合だけ、次のラベルを付ける。

- `確認済み`: 根拠が確認できる
- `推定`: 根拠付きだが未確認
- `提案`: 未承認の案
- `未決定`: 判断材料または決定が不足
- `承認済み`: ユーザーまたは権限を持つ主体が承認した判断

`承認済み` には、可能なら承認日または参照先を付ける。Codex自身の推奨を承認として扱わない。

## 仕様の最小構造

```markdown
# <機能名>

## 目的
## 対象範囲 / 対象外
## 要件
<!-- 安定したIDが追跡に役立つ場合だけ REQ-001 のようなIDを使う -->
## 品質・運用要件
## 受け入れ条件
## 前提・未決定事項
```

## 設計の最小構造

```markdown
# <機能名> 設計

## 設計目標と制約
## 既存設計との関係
## 責務と主要フロー
## データと外部契約
## エラー・セキュリティ・運用
## トレードオフと代替案
## 要件との対応
## 未決定事項
```

## 決定記録の最小構造

```markdown
## <決定名>

- 状態: 提案 | 承認済み | 却下 | 置換
- 日付:
- 背景:
- 決定:
- 理由:
- 代替案:
- 影響:
- 関連要件・設計:
```

## トレーサビリティ

IDや対応表は、複数成果物間の変更漏れを実際に防げる場合だけ導入する。最低限、重要な要件について次を追跡できればよい。

```text
目的 -> 要件 -> 設計判断 -> 受け入れ条件（-> 実装・テスト）
```

リンク切れや重複管理を増やすなら、単一文書内の参照や短い表を優先する。
