# 成果物の選択と最小テンプレート

既存資料を優先し、同じ役割のファイルがある場合は新しい体系を追加せず更新候補を示す。ファイル名はプロジェクト規約へ合わせる。

## 選択基準

| 成果物 | 作る・更新する条件 |
|---|---|
| `AGENTS.md` | Codexが複数作業で継続して守る実行規則がある、または通常実装から承認済み設計資料を参照させる必要がある |
| `docs/constitution.md` | プロダクト目的や設計原則が、個別機能を越えて判断を制約する |
| `docs/architecture.md` | システム境界、責務、データ・依存関係の全体像を共有する必要がある |
| `docs/decisions.md` | 複数の重要判断を軽量に記録する。既存ADRがあればそちらを使う |
| `specs/<feature>/spec.md` | 機能の目的、要件、対象外、受け入れ条件を独立して管理する価値がある |
| `specs/<feature>/design.md` | 機能固有の責務、データ、契約、主要フロー、例外を残す必要がある |
| `specs/<feature>/tasks.md` | 合意済み設計を複数の検証可能な実装単位へ分解する必要がある |

小規模な変更なら、既存Issueや単一の仕様書の節だけで十分なことがある。空のファイルや将来用の雛形は作らない。

## AGENTS.mdによる設計方針の継承

承認済みの設計方針が、今後の通常実装やレビューでも継続して守られる必要がある場合は、対象範囲に適用される既存の `AGENTS.md` を確認する。

`AGENTS.md` には設計内容を複製せず、次だけを記載する。

- 正式な設計資料の参照先
- どの変更で参照が必要になるか
- 実装と設計が矛盾した場合の扱い
- 設計資料を変更する際に必要な承認や同時更新

承認されていない `提案` や `推定` は、通常実装を拘束するルールとして `AGENTS.md` へ記載しない。

既存の `AGENTS.md` がある場合は、その適用範囲と既存構成を維持して必要最小限を追記する。より狭いディレクトリだけに適用する方針は、可能ならその範囲に近い `AGENTS.md` へ置く。

`AGENTS.md` の変更が依頼範囲に含まれる場合は参照ルールを追記する。依頼範囲外の場合は無断で変更せず、追記先と具体的な文案をユーザーへ提案する。

記載例:

```markdown
## Design references

- Agent機能を変更する前に `docs/architecture.md` を確認する。
- 認証、認可、外部API、データ所有、会話保持方式を変更する場合は、実装前に設計への影響を整理し、必要な承認を得る。
- 実装と設計資料が矛盾する場合、どちらかを無断で正とせず差分を報告する。
- 承認済みの設計変更では、実装、テスト、設計資料を同じ変更単位で更新する。
```

## 共通の状態表現

主張や判断に必要な場合だけ、次のラベルを付ける。

- `確認済み`: 根拠が確認できる
- `推定`: 根拠付きだが未確認
- `提案`: 未承認の案
- `未決定`: 判断材料または決定が不足
- `承認済み`: ユーザーまたは権限を持つ主体が承認した判断

`承認済み` には、可能なら承認日または参照先を付ける。Codex自身の推奨を承認として扱わない。

## 全体設計文書の扱い

次のテンプレートは、選択基準により文書が必要と判断された場合だけ使う。テンプレートに合わせるためにファイルを新設したり、情報のない節を空欄で残したりしない。同じ役割の既存文書がある場合は、その構成を尊重して必要な内容だけを更新する。

文書内では、承認済みの方針と、確認済みの現状、提案、未決定事項を混同しない。詳細な判断履歴が既存ADRや `docs/decisions.md` にある場合は複製せず参照する。

## プロダクト原則の最小構造

```markdown
# <プロダクト名> Constitution

## 目的と対象範囲
## 設計原則
## 変更してはならない制約
## 判断の優先順位とトレードオフ
## 例外・改定ルール
```

技術スタックや現在のコンポーネント構成は、プロダクト原則ではなく全体アーキテクチャへ記載する。

## 全体アーキテクチャの最小構造

```markdown
# <システム名> Architecture

## システム概要と境界
## コンポーネントと責務
## データと外部連携
## 主要フローと横断方針
## 主要な設計判断
## リスク・未決定事項
```

主要な設計判断には判断の全文を複製せず、概要と既存ADRまたは `docs/decisions.md` への参照を置く。主要フローと横断方針では、認証・認可、データ整合性、監査、エラー処理、可用性、セキュリティ境界、デプロイ・運用のうち、システム全体へ影響するものだけを扱う。

## 仕様の最小構造

```markdown
# <機能名>

## 目的
## 対象範囲 / 対象外
## 要件
<!-- 安定したIDが追跡に役立つ場合だけ REQ-001 のようなIDを使う -->
## 品質・運用要件
## 受け入れ条件
## 前提・未決定事項
```

## 設計の最小構造

横断的な観点は、対象機能で必要なものだけ記載する。該当項目を埋めるために不要な設計や「該当なし」の一覧を増やさない。

```markdown
# <機能名> 設計

## 設計目標と制約
## 既存設計との関係
## 責務と主要フロー
## データと外部契約
## 認可・監査・整合性・エラー・運用
## トレードオフと代替案
## 要件との対応
## 未決定事項
```

## 設計変更時の更新確認

重要な設計変更が承認された場合は、変更する概念、要件ID、コンポーネント名、データ名、API名、既存文書への参照を検索し、影響する資料を確認する。

変更内容に応じて、次の既存資料を確認する。

- `docs/constitution.md`: プロダクト目的、設計原則、変更不可の制約
- `docs/architecture.md`: システム境界、責務、データ、外部連携、横断方針
- `specs/<feature>/spec.md`: 要件、対象外、受け入れ条件
- `specs/<feature>/design.md`: 責務、処理フロー、データ、契約、例外処理
- ADRまたは `docs/decisions.md`: 判断、理由、代替案、置換関係
- `specs/<feature>/tasks.md`: 合意済み設計から導かれた未完了作業
- `AGENTS.md`: 通常実装が参照する設計資料と変更ルール
- テスト・運用資料: 外部から観測できる仕様、移行、監視、復旧手順

すべての資料を機械的に更新しない。変更の影響を受ける既存資料だけを更新し、新しい文書は既存の文書体系では表現できない場合に限って作る。

依頼範囲内で必要な資料を更新できない場合は、整合したとみなさず、未更新の資料、想定される差分、必要な次の対応を明示する。文書の移動や名称変更を行った場合は、`AGENTS.md`、ADR、他の設計資料からのリンクも確認する。

過去の決定が新しい決定で置き換えられる場合、古い記録を削除したり、新しい結論に書き換えたりしない。

- 古い記録の状態を `置換` にする
- 置換日と新しい決定への参照を記録する
- 新しい記録から置換した古い決定を参照する
- 当時の背景、選択肢、理由は保存する

誤記修正を除き、過去の決定を現在の判断で遡及的に書き換えない。

## 決定記録の最小構造

```markdown
## <決定名>

- 状態: 提案 | 承認済み | 却下 | 置換
- 日付:
- 背景:
- 決定:
- 理由:
- 代替案:
- 影響:
- 関連要件・設計:
```

## トレーサビリティ

IDや対応表は、複数成果物間の変更漏れを実際に防げる場合だけ導入する。最低限、重要な要件について次を追跡できればよい。

```text
目的 -> 要件 -> 設計判断 -> 受け入れ条件（-> 実装・テスト）
```

リンク切れや重複管理を増やすなら、単一文書内の参照や短い表を優先する。
