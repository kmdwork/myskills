# Issue From Request

人間の要求を、既存プロジェクトと整合した実装可能なGitHub Issueへ整理する。Issueや文書を増やすこと自体を目的にしない。

## 責務と境界

- 主な入力は、まだIssue化されていない機能追加、仕様変更、不具合改善などの要求とする。
- 成果物は、背景、変更範囲、外部から見える要件、検証可能な受け入れ条件、重要な制約を含む簡潔なIssue案とする。
- Issueの作成・変更は外部への書き込みである。ユーザーが明示的に依頼した場合だけ実行し、それ以外はIssue案を提示する。
- ソースコード、テスト、設定、DB、ブランチ、コミット、PRを変更しない。Issue作成後も実装へ自動的に進まない。
- 既存Issueから実装フェーズや計画用Draft PRを作る依頼には使わない。Issue化を目的としない設計相談、設計意図の復元、アーキテクチャ評価にも使わない。

## 1. 依頼と既存プロジェクトを調べる

最初から質問を列挙せず、依頼に関係する範囲を先に調査する。

- 適用される `AGENTS.md` とリポジトリの作業規則
- 関係するコード、テスト、設定、マニフェスト
- DB定義、マイグレーション、必要なら適用済みDB状態
- 既存docs、ADR、関連Issue・PR
- 現在の外部契約、認可、データ所有、状態遷移

全ファイルを網羅的に資料化しない。既存プロジェクトがない場合は、プロダクト目的、利用者、MVP範囲、重要な品質要件、データ所有、システム境界など、最初のIssueを実装可能にする情報だけを整理する。

証拠の役割を混同しない。

- コード、テスト、設定、DBは、現在の動作と構造を確認する主な証拠である。
- Issueは、今回合意する要求、範囲、受け入れ条件を記録する。
- docsやADRは、継続的な設計原則、重要な業務ルール、外部契約、決定理由を保持する。
- Issue、PR、Gitは、変更経緯、議論、作業証跡を保持する。

実装と承認済み仕様が食い違う場合は差分を示し、無断でどちらかを正としない。

## 2. 事実と判断を分ける

必要な主張だけを次の状態で整理する。

- `確認済み`: コード、テスト、文書、実行結果などの根拠を示せる
- `推定`: 根拠はあるが確認されていない
- `提案`: Codexが提示する未承認の変更や判断
- `未決定`: 実装範囲または受け入れ条件を左右する判断が不足している
- `承認済み`: ユーザーまたは権限を持つ主体が合意した

調査で解決できる事項はユーザーへ聞かない。高影響な未決定事項だけを、影響、選択肢、推奨案とともに確認する。

事前確認が必要な例:

- 認証、認可、プライバシー、信頼境界
- 永続データ、移行、削除、互換性
- 公開API、イベント、ファイル形式、外部連携
- 重要な責務移動やユーザーから見える複数の妥当な振る舞い
- 大幅な運用負荷、コスト、性能、可用性のトレードオフ

未決定事項が実装開始を妨げる場合は、解消前にIssueを確定・作成しない。妨げない場合は未決定事項と判断時期をIssue案に残せる。

## 3. Issue案を組み立てる

必要な項目だけを選び、空の見出しや「該当なし」を並べない。既存のIssueテンプレートがあれば優先する。

```markdown
## 背景・目的
## 変更範囲 / 対象外
## 要件
## 受け入れ条件
## 制約・既存設計への影響
## 決定済み事項 / 未決定事項
## 関連するコード・docs・Issue
## PRで更新すべき永続資料
```

- 要件は利用者や外部システムから見える振る舞いとして書く。
- 受け入れ条件は観測・検証可能な結果として書き、実装タスクの列挙にしない。
- テスト層、データ移行、後方互換性、失敗時・ロールバック時の振る舞いは、変更の性質上必要な場合だけ含める。
- クラス名、関数分割、内部ファイル構成など、実装時に安全に決められる事項は固定しない。
- API契約、重要なデータ構造、認可など、後から変える費用が高い事項はIssue作成前に合意する。
- 今後も有効な設計原則や契約が変わる場合だけ、PRで更新すべき既存docsを記載する。Issueごとの追加文書を機械的に要求しない。

要求が一つのレビュー可能な変更として大きすぎる場合は、親子Issueまたは複数Issueへの分割案を示す。ユーザーの依頼なしに複数Issueを作成しない。

## 4. Issueを作成または提示する

Issue作成を明示的に依頼され、実装を妨げる未決定事項がなく、対象リポジトリを確認できた場合だけ作成する。

作成前に、タイトル、本文、対象リポジトリが依頼と一致することを確認する。既存Issueとの重複が疑われる場合は、先に検索して差分を示す。ラベル、担当者、マイルストーンは、ユーザーの指定または明確なリポジトリ規約がある場合だけ設定する。

作成後は次を報告する。

- Issueのリンクと対象リポジトリ
- 確定した範囲と主な受け入れ条件
- 残した仮定または未決定事項
- 実装PRで更新が必要な永続資料
- 実装や計画用PRへ進んでいないこと

Issueを作成しなかった場合は、Issue案と、作成を止めた未決定事項または不足する権限・対象情報を示す。
